# B 站插件与统一通知：实施计划

更新日期：2026-10-01

状态：第一至第四步已实施并通过自动验证；第五至第六步待实施。第四步界面待用户手动检查，真实账号和 Windows 通知尚未人工验收。

本计划接续 [按来源恢复通知：实施步骤](source-notification-restoration-plan.md)。旧计划的第一至第四步已实施，人工验收尚未完成；本计划处理后续发现的 B 站查询问题、通知范围、统一添加入口与通知文案，不重新编号旧步骤。

## 1. 已确定的产品行为

### 1.1 B 站通知始终是 UP 的事件

“哔哩哔哩”卡片是通知配置入口，不是一种独立的站点事件。通知内容来自 UP 的视频更新、开播；历史记录和稍后再看不发送更新通知。不得把真实通知的作者名称替换成“哔哩哔哩”，也不再提供一个与 UP 通知并列的“整个 B 站来源通知”。

B 站配置提供两个范围：

- **全部已关注 UP**：当前登录账号关注的 UP 都参与通知，遵守更新、开播类型开关；以后新关注的 UP 也参与。不会把全部关注逐一复制成自定义通知项。
- **自选 UP**：只通知用户选择的 UP，各 UP 保留更新、开播开关。选择通知对象不等于在 B 站关注该 UP，也不创建独立 FeedPeek 来源。当前数据来自关注动态和关注直播，因此未关注的 UP 暂不支持独立通知。

“全部”指该账号已关注的 UP，不是 B 站全站。更新范围沿用插件当前视频更新能力，不承诺插件尚未提供的所有动态类型。

更新和开播仍是两个独立通知类型。选择全部不会强制打开用户关闭的类型开关；选择自选也不会自动开启已有 UP 的关闭开关。

这里将“UP 更新”理解为以 UP 为对象的事件，沿用已确认的更新、开播能力，不因本次通知名称调整取消现有 B 站开播通知。

### 1.2 与全局三态的关系

保留全局名称、枚举值与持久化值：**不通知 / 所有来源更新 / 自定义来源通知**。

| 全局模式 | RSS/Atom、兼容直播间 | B 站 |
| --- | --- | --- |
| 不通知 | 不执行通知轮询或发送 | 不执行通知轮询或发送，保留配置 |
| 所有来源更新 | 全部有效来源，遵守全局更新/开播开关 | 全部已关注 UP，遵守全局更新/开播开关；保存的自选配置暂不参与筛选 |
| 自定义来源通知 | 按各自通知规则 | 按 B 站保存的全部/自选范围和类型开关 |

B 站详情明确说明范围选择用于“自定义来源通知”；全局模式覆盖时说明当前有效范围，不让用户误以为保存自选后全局“所有来源更新”也会变成自选。切换全局模式不清空 B 站配置。

原生插件 `notifications.autoAddToCustom=false` 继续有效：安装、登录或同步关注名单不会自动生成 B 站通知项或整批 UP 项。用户通过统一“添加通知”入口主动配置 B 站。来源的创建方式与通知规则的创建方式相互独立。

### 1.3 已有来源列表与插件分组

通知页自动展示全部已添加来源，取消手动添加来源通知的窗口和入口。RSS/Atom 使用原始 `SettingsCard`；插件来源按完整 provider 身份分组为 Toolkit `SettingsExpander`，外层显示插件名称和圆形图标，展开后显示直播间等通知项及已保存自选作者，正文副标题不重复插件名称；作者插件的来源级范围配置移到 ItemsFooter 的“通知设置 / 设置”入口。

已有关闭值、范围和名单保持不变。尚无通知配置或曾删除配置的来源仍可查看，但以关闭的虚拟配置展示；仅点击开关、保存范围或添加作者时持久化，不因为显示卡片而自动启用通知。停用或暂不可用的来源仍显示状态。来源移除后不再展示对应组项。

插件展开区底部通过原生 `ItemsFooter` 固定提供“通知设置”和“添加通知”操作，两个页脚卡片均使用用户提供 Toolkit 示例中的 `DefaultSettingsExpanderItemStyle`，不带 HeaderIcon；单一来源无重复副标题，多个来源以名称区分操作对象。是否提供由插件 manifest 的 `creator.following` / `creator.resolve` 作者能力和实际通知 Feed 决定，不检查 B 站名称或 ID。B 站插件已经声明这两个能力，无须新增清单字段；RSS/Atom 和仅直播间能力的兼容插件没有作者添加按钮。同一插件多个来源各有自己的添加入口，传递完整 provider/source 身份。

添加按钮限定当前来源搜索已关注作者，输入名称后显示匹配结果，支持 ID 与链接查询，不自动展开整个关注名单。保存作者保留已有全部/自选范围和关闭值；全部范围下也保留添加按钮，新增的自选偏好在切回自选后生效。重复作者进入已有详情。

全部范围下隐藏自选作者卡片但保留数据；人数来自保存的选择，不因临时查询失败变化。来源及插件配置通过开关关闭通知，不删除通知卡片；只有自选作者详情保留删除操作，不取消站点关注。来源设置和插件设置的详情跳转保留，没有“来源和插件设置”通用按钮。

### 1.4 通知文案

| 事件 | 标题 | 第二行 |
| --- | --- | --- |
| RSS/Atom 更新 | `源名称|更新标题` | 条目摘要或正文摘要 |
| B 站视频更新（全部、自选一致） | `UP名称|视频标题` | 视频简介或插件实际取得的更新内容 |
| B 站、兼容直播间开播 | `主播名称|直播标题` | `正在直播` |

分隔符固定为半角 `|`。直播标题缺失时用“开播”。缺少更新内容时省略第二行，不重复标题，不生成不存在的简介。摘要转纯文本、规范空白并限制展示长度，完整标题和正文仍保留在原条目中。

格式由 App 统一处理；插件只返回名字、标题、摘要、头像、封面和地址。通知点击、打开网页及有能力的稍后再看按钮继续使用原事件身份。

## 2. 当前代码证据及责任划分

以下为 2026-10-01 的本地源码检查，未请求用户实际账号数据，也未证明已安装的插件包一定与源码相同。

| 位置 | 当前问题 | 实施归属 |

| 更新轮询 | 后台只取第一页，插件的页大小由站点接口决定 | 插件正确提供游标；Host 在通知查询中有界追赶，避免漏掉中间页 |

插件负责 B 站接口、认证结果、关注关系、站点地址解析、分页、数据映射与站点动作。App/Core 负责来源和规则持久化、模式选择、统一界面、基线、筛选、去重和 Windows 通知。不能在 App 中加入 B 站 API、URL 规则或按插件 ID 分叉的通知业务。

当前自动来源创建代码与 `AGENTS.md`、架构文档的描述有差异。本计划不顺手重做来源创建流程，不把“添加通知”变成安装、登录、创建来源的混合动作；实施时单独记录该差异，避免依靠自动重建来源修复插件临时 Map。

## 3. 分步实施

### 第一步：修正 B 站插件查询与来源生命周期

交付目标：关注列表完整可靠，直播结果不产生假离线，来源定义能跨运行环境访问。

1. 关注查询逐页读取并去重 UID。终止条件依据接口实际返回的分页信息，设置请求数量上限、重复页检测和取消链路；达到上限不能伪装为完整名单。
2. 直播查询核对接口分页字段并收集全部在线页，按稳定作者/房间身份去重。部分失败、达到上限或关键结构缺失时返回 `isComplete=false` 或明确错误；全失败不返回成功空集合。真实完整的空列表才表示没有在线房间。
3. 严格校验各接口的错误码与必需数据结构，保留登录过期、风控、限流等已有错误分类。允许合法空列表，不把缺字段视为“零关注/全部下播”。
4. `source.get/listFeeds` 根据已注册上下文恢复固定 Feed 定义和配置，不要求同一 JS realm 先执行 `source.create`。持久化来源名由 Host 保留，不用临时回退名覆盖。`source.delete` 幂等，已无临时记录不妨碍 Host 删除来源。
5. 拆出可复用查询/映射逻辑；缓存必须限定账号与来源，具备失效策略，失败不更新成空名单，不缓存认证失败为未关注。
6. 补插件测试：超过 50 个关注、第二页作者、重复页、取消、分页失败、完整零在线、部分在线结果、响应缺字段、销毁并重建 realm 后查询/删除来源。

验收：独立插件测试通过；相关 Host/Runtime 回归通过。不改通知页面或现有通知范围。

### 第二步：建立通用作者解析能力，修复“已关注显示未关注”

交付目标：作者输入查询直接得到身份、资料和关系；查不到与未关注有明确区别。

1. 在插件合同中增加可选作者解析方法/能力（建议 `creator.resolve`，具体 DTO 和错误枚举在此步定稿），输入为原始链接或 ID，带有效来源与账号上下文。
2. 返回作者 ID、名称、头像、个人页、支持的通知类型，以及已关注/未关注/未知状态。网络失败通过错误表达；没有接口支持不得假装返回“未关注”。
3. B 站复用已有按 UID 查询关系的逻辑，并核实可用的作者资料查询接口。具体链接归属、缺协议、个人页子路径及 UID 解析在插件完成；不要用“关注/取消关注按钮是否出现”替代正式关系字段。
4. Host 校验完整身份、返回地址、字段与能力。App 按 URL 归属/插件声明路由；纯数字 ID 存在多个候选插件时让用户选择提供者，不随便选第一个同 ID 作者。
5. 作者候选读取以 `creator.following` 等能力和有效来源为准，不绑定固定 Feed 名称。不同提供者分别返回成功/失败状态；一个插件失败不阻断其他来源或作者展示。
6. 无作者解析能力的旧插件继续使用其关注列表，但只有能证明完整且成功的结果才据此判定未关注；否则说明无法确认。作者开关按 `supportedNotificationKinds` 与有效 Feed 能力的交集显示。
7. 测试第二页 UP、已关注/未关注、缺协议链接、`/UID/video`、跨插件同 ID、账号过期、查询失败和旧插件兼容。

验收：原有已关注 UP 可正常添加；错误信息准确；没有新增隐式关注动作。

### 第三步：持久化“全部已关注 UP / 自选 UP”并接入筛选

交付目标：范围、类型开关和自选名单可独立保存，后台遵守有效模式。

1. 建议增加通用“作者通知范围”策略，按 `providerId + sourceId` 关联，记录全部/自选和可用类型的开关。资格由作者能力、Feed 通知能力及插件声明共同决定，不由 B 站 ID 白名单决定。RSS/独立直播间继续使用来源规则。
2. 保留自选规则完整键 `providerId + sourceId + creatorKey` 及原有更新/开播布尔值。配置名称、头像与账号名不作为身份键；全部策略不生成每个 UP 的持久规则。
3. 新手动 B 站配置默认自选；由用户明确改为全部。全部与自选切换保留自选名单及各开关。自选下类型总开关与该 UP 开关同时允许才通知；全部下自选名单暂不参与。
4. 全部覆盖当前及以后已关注的 UP。新增关注对象纳入通知时先建立该 UP 的成功查询基线，已有视频或正在直播不立即提醒；仅初始化新对象，不重置其他 UP 的正常监控。自选 UP 后续取消关注时保留规则并标注不可用，不继续声称其可收到关注动态通知；查询失败保留原配置，不推断取消关注。账号变更/重新登录重新验证关系、清除账号相关缓存并重建运行基线，不能把旧账号资料当新账号资料。
5. 按第 1.2 节明确优先级：全局不通知 > 全局有效范围/类型；仅在自定义模式应用此策略。每个事件按完整条目或直播身份去重，命中全体和作者条件也只发送一次。
6. 迁移：只有旧 UP 规则时建立自选策略并原样保留开关；只有旧 B 站来源范围规则时转换为全部策略并保留类型值。这里的“旧”指已正确关联当前插件和来源的现有规则；旧 BiliRadar 的 `feedpeek.video-site` 身份不能仅凭 UID 静默重绑到 `feedpeek.bilibili`，保持已有兼容/清理边界，不另做跨账号迁移。迁移必须幂等，不能自动打开关闭的类型或创造新规则。
7. 旧来源规则和作者规则同时存在时，按更新/开播分别计算原来的等效筛选范围。若两类范围不同，用分类型策略保存并在详情显示原值；普通“全部/自选”操作明确同时应用两类，只有用户主动操作才统一。不能通过迁移把“全部视频 + 个别 UP 开播”扩大成“全部开播”。
8. 源删除和卸载清理策略及作者规则；插件停用保留设置但停止通知；删除通知配置不删除来源或 B 站关注。继续遵守 `autoAddToCustom=false`。
9. 测试全局三态 × 全部/自选 × 更新/开播开关、切换后恢复、新关注 UP 的静默基线、迁移重复执行、混合旧范围、不同旧插件身份不重绑、删除和停用，以及不自动生成全部 UP 卡片。

验收：纯筛选与持久化测试通过；旧配置迁移不扩大通知范围。UI 在下一步接入。

### 第四步：统一“添加通知”和 B 站详情

交付目标：自动展示已有来源，插件展开区显示通知配置，底部按插件能力提供作者添加。

1. 移除手动添加来源通知入口；已有来源直接展示。复用原 `SettingsCard`、Toolkit `SettingsExpander` 和作者搜索 `ContentDialog`，不增加库。
2. RSS/Atom 直接卡片、插件按 provider 分组，展开正文为通知项及自选作者，作者来源级设置移至原生 ItemsFooter，底部按 manifest 作者能力显示添加通知；不按 B 站 ID 判断。未配置来源显示关闭的虚拟项，用户编辑才持久化。
3. B 站详情提供全部/自选范围及更新、开播开关；自选时可添加 UP。按第三步保留少量旧配置的分类型范围，不把迁移差异隐藏成错误的单一选项。
4. UP 卡片与 B 站配置关联；进入详情保留名称、圆形头像、类型开关、删除、来源/插件跳转。全部时隐藏自选列表、保留数据，说明自选名单当前不参与筛选。
5. 简体/繁体、错误说明、键盘焦点、自动化名称同步；取消/关闭对话框后不让过期异步查询覆盖页面或误保存。
6. 沿用设置页内容 Margin、条件元素合并、关闭 InfoBar 折叠、默认 HeaderIcon 尺寸与圆形裁切；不放大卡片字体或内边距。实施前核对本机官方示例，优先复用已采用控件。

验收：构建和逻辑验证通过后，由用户手动比较列表、详情、窄窗口和状态提示。需截图采样的布局验收在明确进行 UI 检查时执行，不自行启动应用。

### 第五步：更新分页追赶与通知文案

交付目标：检查间隔内跨页的新更新不漏报，标题和内容符合第 1.4 节。

1. 插件保持真实游标和 `hasMore` 语义；Host 通知查询从最新页追赶至上次成功查询边界，设置页数/请求/时间上限，识别游标重复与无进展，遵守取消和限流。不能依靠一次传入 `pageSize=200` 假定插件返回 200 条。
2. 追赶使用独立通知进度，不覆盖前台“加载更多”的历史游标，不把用户浏览历史当成新更新。页面错误不推进成功边界，已可靠取得的事件仍按完整身份去重；达到上限保留可续查状态并记录缺口，不能默认为已追到边界。
3. 每次进程启动、范围或开关新开启、来源更改、账号改变时，首次成功查询建立基线。B 站分页补查结合可信发布时间和基线锚点过滤基线前内容，不能仅因为旧条目此时第一次入库就推送历史；无法可靠判断新旧时采用静默记录策略。

2. 插件外层显示插件名称、圆形图标；展开后是该插件的通知项，副标题不重复插件名。B 站来源配置不混入通知列表，底部使用无图标原生 ItemsFooter 显示通知设置和添加通知，直播间兼容插件不显示作者按钮；两个插件或同插件多个来源搜索不能串身份。添加后保留展开状态。
3. B 站范围切换全部/自选保持类型开关、旧混合状态和作者名单；全部时不展开关注作者，底部添加仍可保存自选偏好。名称搜索、ID/链接查询、重复作者、关闭查询、登录失效应正确处理。
4. 窄窗口、小高度及浅色/深色检查折叠、候选滚动、原卡片尺寸与圆形头像回退。界面由用户手动检查；未自行启动应用或采样截图。实际通知与分页追赶留到第五步。
