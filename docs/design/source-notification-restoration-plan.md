# 按来源恢复通知：实施步骤

更新日期：2026-10-01

状态：第一至第四步已实施；第五步人工验收待进行。来源通知卡片、详情编辑、后台来源/作者规则筛选、事件去重和每次启动的运行基线均已接入；实际 Windows 通知与界面仍需人工验收。

后续计划见 [B 站插件与统一通知：实施计划](bilibili-notification-unification-plan.md)。B 站通知范围确定为“全部已关注 UP / 自选 UP”，两种范围的实际通知均显示 UP 名称；统一添加入口、插件查询修复、分页追赶与文案调整按新计划单独分步实施。本页保留既有恢复过程与实施记录，新计划的界面及范围设计优先于本页旧的双菜单和通用 B 站来源规则展示方式。

## 目标与边界

保留通知对象的三个模式及用户指定的名称：**不通知 / 所有来源更新 / 自定义来源通知**。`不通知` 不轮询通知；`所有来源更新` 对所有已启用且声明支持通知的 Feed 使用现有全局“更新/开播”开关；`自定义来源通知` 只按自定义列表中的规则发送通知。切换模式不清空规则或用户设置。

添加 RSS/Atom 或 AngleLive/LiveParse 兼容直播间来源时，若当前处于“自定义来源通知”，自动把该来源加入自定义通知列表。普通原生插件通过清单声明是否自动加入；默认**不自动加入**，哔哩哔哩插件显式声明不自动加入。B 站已有的手动自定义 UP 规则保留，不把已关注的每个 UP 自动复制为通知项。

自定义列表改用“来源”页的 `SettingsCard` 风格：显示圆形图标、名称、来源类型和开关状态。列表卡片不放删除按钮；点击进入通知详情页。详情页按能力显示“更新通知”“开播通知”开关，并提供“打开来源设置”、插件来源的“查看插件”和“删除此通知项”。不引入新的控件库，列表复用原始 `SettingsCard` 模板；圆形头像放入默认 `HeaderIcon`，详情沿用 `PersonPicture`，间距沿用设置页资源。

## 当前实现中需要改造的点

| 位置 | 现状 | 目标 |
| --- | --- | --- |
| `AppSettings.NotificationTargetMode` | 三态已经存在；部分 XAML/资源仍带 UP/作者措辞 | 保留枚举值和持久化值，同步三种用户指定文案 |
| `NotificationCreatorSubscription` | 仅用 `providerId + sourceId + creatorKey` 表示手动作者规则 | 保留旧规则；另建来源规则，不复用空 `creatorKey` 冒充来源 |
| RSS 来源 | `updates` Feed 已声明 `SupportsNotifications=true`，添加时已做首次 Feed 拉取 | 自定义模式下创建一项“更新通知”；继续不通知历史条目 |
| LiveParse 兼容来源 | `feed.getLive` 能查直播间，`source.create` 的直播 Feed 却写成 `SupportsNotifications=false` | 修正为 `true`；自定义模式下每个已添加房间产生一项“开播通知” |
| 原生 B 站插件 | `updates/live` 为 `true`，`history/viewLater` 为 `false` | 维持能力；清单声明不自动加入，仍可手动添加 UP 规则 |
| 通知轮询 | 按 `feedId=updates/live` 取数据，不读取 `SupportsNotifications`；自定义模式只按作者过滤 | 依据实际 Feed 能力和来源/作者规则筛选，避免无能力 Feed 进入通知 |
| 基线 | 更新、直播的已知 ID 存在 LocalSettings；启动后可能补报停机期间的变化 | 每次进程启动、来源新增或开关重新开启时，以首次**成功**查询建立基线 |

## 实施顺序

### 1. 先固定规则身份和插件声明

1. 新增独立的来源通知规则，身份键为 `providerId + sourceId`；规则记录更新、开播两个开关及各自对应的 `feedId`。显示名和图标从现有来源读取，不作为身份键。手动 UP 规则继续使用现有的 `providerId + sourceId + creatorKey`，两类规则在页面上统一展示。
2. 只根据来源实际存在、已订阅且 `SupportsNotifications=true` 的 Feed 决定可显示的开关。RSS/Atom 仅“更新”；LiveParse 仅“开播”；原生插件按其 Feed 定义。后台处理时还要检查来源与插件是否启用。
3. 给原生插件清单增加可选的“加入自定义通知列表”声明，默认 `false`；在 `FeedPeek-Plugin` 的哔哩哔哩清单中显式写 `false` 并同步 README。内置 RSS 和 LiveParse 转换出的直播间来源采用宿主定义的自动加入策略，不依赖插件 ID 白名单。此声明只决定**自动创建规则**，不能绕过 `SupportsNotifications`。
4. 修正 LiveParse `source.create` 的直播 Feed `SupportsNotifications` 为 `true`，并验证其仍只产生直播 Feed，不出现更新开关。

### 2. 持久化、补齐和删除

1. 来源规则存入与来源身份关联的持久层，和现有作者规则分开；推荐放在 FeedPeek SQLite 中，便于按 `providerId/sourceId` 查询和清理。保存用户明确选择的开关值及规则来源（自动/手动）。
2. 在添加来源**成功保存之后**执行幂等同步：仅当模式为“自定义来源通知”、来源符合自动加入策略，且规则尚不存在时创建。新规则的可用开关默认开启，但不改变用户现有的通知对象模式；处于“不通知”时不能因此开始推送。
3. 首次打开新通知设置页时对已有来源运行同一同步；若当时不是自定义模式，切换进入自定义模式时再同步。同步只补缺项：已存在规则的开关状态、显示顺序和手动 UP 规则均不得被覆盖。升级后第一次同步不把 B 站插件自动加入。
4. 详情页“删除此通知项”是用户明确退出自定义列表。对自动来源记录一个按 `providerId/sourceId` 的“不要自动补回”标记，避免下次打开设置页又被补齐；手动添加入口可撤销这一标记。删除整个来源时同步清理规则、标记和该来源的运行基线；重新添加时按新来源处理，即使 RSS 地址生成相同的 `sourceId`，也不继承已删除来源的标记。停用插件保留用户规则但不通知，卸载插件则清理其来源规则。
5. 如需迁移旧作者规则，保留原始布尔值和身份，不根据新的来源规则覆盖。对过时、找不到来源的规则做一次性清理或标注，避免静默把旧 B 站规则绑定到新插件身份。
6. 旧兼容来源的直播 Feed 已在 SQLite 保存过 `SupportsNotifications=false`，修改转换脚本不会自动改写这些记录。此批次按当前加载插件的 `liveparse-v1` runtime 识别宿主生成的直播 Feed，幂等修正能力标记后再补齐来源规则；不能借此重新开启用户关闭的通知开关。

### 3. 重做通知设置页，而不改变三态语义

1. 统一 XAML、简体/繁体资源和辅助说明中的“不通知 / 所有来源更新 / 自定义来源通知”；去掉把所有来源都叫作“UP”“视频”的文案。检查频率保持原位置和持久化行为。
2. “所有来源更新”仍使用全局更新、开播开关；“自定义来源通知”显示 `SettingsCard` 列表和手动添加入口。自动来源卡片与手动 UP 卡片用不同副标题明确身份，切换模式不删除卡片。
3. 点击卡片进入通知详情页：仅渲染对应来源支持的通知开关；RSS 显示“打开来源设置”，插件来源另显示“查看插件”；删除按钮仅在详情页。来源/插件被删除或禁用时，详情页要有明确回退，不导航到失效对象。
4. 列表和详情页沿用“来源”页的圆形图标与默认回退。适配窄窗口、键盘焦点、无障碍名称及浅色/深色/高对比度；条件卡片折叠时不留下额外 4px 空隙。

### 4. 改造后台筛选和运行基线

1. 通知会话从订阅与 Feed 定义读取能力，不再只凭固定 `updates/live` ID 决定资格。`所有来源更新` 忽略自定义列表但遵守全局类型开关；`自定义来源通知` 对来源规则和手动作者规则取并集，用事件的完整身份去重，避免同一条内容弹两次。
2. **每次 App 启动都建立本次进程的通知基线**：对每个已启用更新 Feed 和直播来源，首次成功查询只记录当前条目/当前直播状态，不弹通知；即使本地存有上次运行的 ID，也不补报停机期间的更新。第一轮查询失败的来源保持“待建立基线”，直到它首次成功，失败不能被当作空结果。
3. 添加来源、把通知开关由关改开、或从“不通知”切到通知模式时，对新纳入的规则执行同样的首次成功查询基线。RSS 已有的首次 Feed 拉取继续负责内容库存基线；通知发送端仍需独立识别“本次启用后的第一轮”，不能仅依赖旧的全局 Known ID 列表。
4. 直播状态按来源/直播间保存本进程最近一次**成功**观察到的在线集合：首次成功见到正在直播只记录；成功观察到离线后再成功观察到开播才通知。插件/网络查询失败时不清空在线集合、不认定离线，恢复连接后仍在线不误报。一个来源失败不影响其他来源的成功结果或状态。
5. 更新通知只发送基线建立后新插入的条目。通知能力关闭时可继续普通信息流刷新，但不能把关闭期间的旧条目在重新开启时补报。通知重启/重新登录/插件重新启用也按首次成功查询规则处理。

### 5. 验证与验收

1. 单元测试覆盖规则幂等补齐、用户关闭开关不被覆盖、自动项详情删除后的抑制、来源删除清理、B 站显式不自动加入、RSS 仅更新、LiveParse 仅开播、旧手动 UP 规则保留。
2. 通知状态测试覆盖启动时已有新 RSS 条目/正在直播均不弹；启动后新更新、直播间“在线→离线→在线”各正确提醒；首次查询失败后成功只建基线；已知在线时一次失败后仍在线不重复提醒；多个来源部分失败互不影响。
3. 验证三态切换、全局开关与自定义开关的优先级，以及同一事件同时命中来源和作者规则时只弹一次。检查 B 站未登录、插件停用/卸载、应用退出再启动的行为。
4. 构建并运行相关 Core/插件测试后，由用户人工检查通知设置页的卡片、详情导航和实际 Windows 通知。UI 验收不以“能编译”代替；每个阶段都保持可回退。

## 建议的实施批次

按“规则与能力 → 幂等同步和迁移 → 设置页与详情页 → 后台筛选和启动基线 → 测试及人工验收”的顺序提交。前四批完成前不把新通知页视为已恢复：仅出现开关但后台仍按旧作者规则过滤，会造成 RSS/直播间看似启用却不通知。

## 第一步实施记录（2026-10-01）

- Core 新增 `SourceNotificationKey` / `SourceNotificationRule`，来源身份仅由 provider/source 决定，更新和开播分别保存开关及 Feed ID 列表；原有手动作者规则未改动。
- `SourceNotificationCapabilities` 仅收集同一来源的已启用订阅且 Feed 声明支持通知的项目。按 Feed kind 区分更新与开播，插件能力还需允许对应类型；RSS/Atom 仅更新、兼容直播间仅开播。
- `PluginManifest` 增加可选 `notifications.autoAddToCustom`，原生插件缺省为 `false`，非布尔值加载失败；同步 JSON Schema 与插件架构文档。
- LiveParse 转换器显式写 `true`，旧兼容包省略字段时仍采用宿主自动加入策略；`source.create` 的直播 Feed 标记已改为 `true`。旧数据库中的标记修复安排在第二步。
- App 提供 `GetNotificationSourcesAsync`，返回当前可用来源、可用类型和自动加入默认值，只读取规则候选，不保存或补齐通知项。
- 独立 B 站插件清单显式写 `notifications.autoAddToCustom=false`，同步插件 README 与回归断言；更新、开播 Feed 的通知能力保留。
- 验证：相关 Core/Runtime/LiveParse 测试 30/30 通过，独立 B 站插件测试 9/9 通过；App Debug x64 构建通过，0 警告、0 错误。本批次未修改通知 UI，也未执行运行时通知验收。

## 第二步实施记录（2026-10-01）

- SQLite 升级到 schema v3，新增来源通知规则与自动补齐抑制表。两张表均按 provider/source 关联来源，删除来源时级联清理；保留原有来源、订阅、缓存和手动作者规则的保存方式。
- 自动补齐以事务执行“只插入缺项”，保留已有开关值、规则来源及列表顺序。用户删除通知项时原子写入抑制记录；显式手动恢复时原子清除抑制记录并保存规则。详情页入口将在第三步接入。
- RSS 首次拉取成功、插件来源全部选定 Feed 保存完成后，若处于自定义模式，补齐符合宿主/插件策略的通知项；B 站不自动加入。不通知及所有来源模式不会因此生成自动通知项。
- 打开通知页时同步存量来源，切入自定义模式时先完成补齐再发布模式变更。快速切换或页面关闭时，旧异步结果不会覆盖新选择；同步失败保留原模式并提示重试。
- 设置会话及后台通知会话均按已加载插件的 `liveparse-v1` runtime 修复旧直播 Feed 的通知能力标记，不修改通知规则开关；停用插件的来源与规则保留。
- 普通来源删除、退出插件登录导致的来源删除、插件卸载前的来源删除统一清理。SQLite 负责规则/抑制记录级联，AppSettings 清理对应手动作者规则与现有更新/直播 Known ID；首次打开通知页时清理已无对应来源的旧作者规则，不重绑插件身份。
- 验证：来源通知能力/持久化及现有轮询回归测试 18/18 通过，覆盖 v2→v3 升级、设置/监控并发升级、重复同步、重开数据库后的关闭状态、删除抑制与手动恢复、同身份来源重建、并发补齐和兼容能力修复。App Debug x64 构建通过，0 警告、0 错误。
- 本批次未添加来源通知卡片和详情页，未接入后台来源规则筛选/去重及每次启动的新基线。界面和实际 Windows 通知验收分别安排在第三、第四步；暂不要求用户手动检查本批次。

## 第三步实施记录（2026-10-01）

- 通知对象统一为“不通知 / 所有来源更新 / 自定义来源通知”，保留原枚举及持久化值；全局类型文案改为更新、开播，检查间隔保持原行为。
- 来源规则与原有手动作者规则统一展示为来源页同款 `SettingsCard`，标题和描述使用默认模板；圆形头像由原生 `PathIcon` / `ImageBrush` 放入 20px 的 `HeaderIcon` 图标位，缺图或加载失败回退默认来源图标。副标题区分 RSS/Atom、直播间、网站订阅和作者，并显示可用开关状态；列表不放开关或删除按钮。
- 新增独立通知详情页，按当前有效订阅和插件能力显示开关。保存前重新加载身份、能力与规则，保持另一开关及自动/手动标记；停用或异常插件保留规则和已有值，显示暂不可用，并允许进入插件设置恢复。

- 未引入新依赖。先通过 `winapp find-ui` 核对 CommunityToolkit 可点击 SettingsCard 示例，再复用项目现有模板、间距、主题资源和宽窄布局；条件区合并为一个布局子元素，关闭提示时折叠自身。
- 验证：来源通知能力/持久化与轮询回归测试 18/18 通过；App Debug x64 构建通过。未启动应用，按用户偏好保留界面人工验收；间距像素、键盘和主题效果不能视为已验证。
- 人工验收建议：切换三种模式观察间距；确认 RSS 详情只有更新、兼容直播间只有开播；关闭开关后返回/重开仍关闭；删除通知项后重开不补回，再从添加菜单恢复；检查作者卡片、插件停用状态、来源/插件跳转与返回；缩窄窗口并检查浅色/深色/高对比度。
- 本批次仅完成设置 UI 与规则编辑。实际 Windows 通知的来源规则筛选、重复事件去重及启动/新增来源基线仍属于第四步，不用本批次的开关判断通知功能已完全恢复。

### 第三步界面调整：采用默认卡片排版

根据用户对照验收，来源、已安装插件和通知列表均移除塞入 `Header` 的自定义头像/两行文字 Grid，改为默认的 `Header`、`Description`、`HeaderIcon`；不额外设置文字字号、字重、行间距、图文间距或卡片高度。圆形头像复用原生 `PathIcon` 的圆形几何和 `ImageBrush.UniformToFill` 居中裁切，仅占默认 20px 图标位。图片缓存记录失败状态，加载失败和再次打开均回退普通来源图标；卡片卸载时解绑图片失败事件，避免缓存图片持有旧页面。临时样式对比区域及资源已删除。本次仍由用户人工验收视觉效果。

## 第四步实施记录（2026-10-01）

- 后台从当前启用的订阅、Feed kind、通知能力及插件 capability 构造监控对象。所有来源模式遵守全局更新/开播开关；自定义模式取来源规则和手动作者规则的并集，按完整条目/直播间身份去重，不用固定 `updates/live` ID 决定通知资格。
- 新增可单独测试的 `NotificationBaselineTracker`，基线只保存在本进程。每个来源/作者监控对象首次成功查询静默记录；启动、新增规则、重新开启通知、重新登录及插件重新启用后均重新建立对应基线。旧 LocalSettings Known ID 与初始化标志仅保留迁移和清理兼容，不再参与发送决策。
- 更新依据数据库 `FirstSeenAt` 和本次成功基线过滤，已有库存及关闭期间的条目不补推。前后台共享本进程最新普通刷新页，后台遇到 304 仍可识别前台已插入的新条目；加载更多不写入通知快照。同一 Feed 的请求、库存及轮询状态提交跨会话串行，取消等待不会锁住后续查询。
- 直播只以完整成功查询更新在线集合。首次见到在线不提醒；成功见到离线后再次在线才提醒。失败、缺失或未知直播状态，以及部分房间查询失败，均保留上一成功状态；某个来源失败不妨碍其他来源。部分成功内容仍可显示在信息流，但本轮不参与通知基线。
- `PluginLivePage` 增加可选 `isComplete`，旧原生插件省略时默认 `true`。LiveParse 兼容层部分成功返回 `false`，全部失败返回错误；原生插件也可声明部分失败。宿主无法识别原生插件自行吞掉错误并返回完整空结果，因此插件应按此合同报告失败。
- 通知模式、类型开关、规则编辑、来源增删/地址修改、插件启停/升级及登录状态均记录进程内变更代次，即使两次轮询之间快速关开也会重建基线。刷新中修改设置会使旧结果失效并补跑一轮；发送前逐条检查版本和取消状态。通知事件从工作线程切回 UI 调度器，保留原有点击打开及稍后再看动作。
- 来源规则保存的 Feed ID 作为创建时快照；后台每轮用当前有效订阅和能力重新解析有效 Feed ID，仅保留原规则的更新/开播布尔值和自动标记。兼容能力修复或新增 Feed 不会被旧空列表阻挡，也不会重新开启用户关闭的类型开关；新增监控对象首先静默建立基线。
- 自动验证覆盖启动静默、历史过滤、前台插入/后台 304、离线再开播、失败后恢复、首次失败、来源互相隔离、来源/作者重叠去重、快速重建基线、能力变化及关闭状态保留。Windows 通知与界面尚未运行验收。
- 验证结果：相关 Core/Runtime/LiveParse 回归测试 65/65 通过；App Debug x64 构建通过，0 警告、0 错误。未启动应用或触发真实通知，第五步人工验收保留给用户。

### 第五步人工验收建议

1. 先选自定义来源通知并将检查间隔调为 1 分钟。重启时已有 RSS 内容、正在直播的房间都不提醒；新增 RSS 和正在直播的房间也不补报当前内容。
2. 等基线成功建立后，让 RSS 出现新条目；让直播间成功被观察到离线，再开播，各收到一次通知。单纯换直播标题或普通刷新不重复通知。
3. 对已在线的房间临时制造查询失败，恢复后仍在线不报开播；第一次查询失败的新增来源恢复成功时只建立基线。测试期间确认确实经历后台查询，而不只是立即断开/恢复。
4. 关闭再开启一个通知项、切换不通知再恢复、停用再启用插件后，首轮静默，后续新事件正常通知。自定义模式中同时添加同一来源和其作者，事件只收到一次；所有来源模式仅由全局类型开关决定。
5. 检查通知点击打开和支持插件的稍后再看按钮；B 站保持手动 UP 规则、不自动加入来源通知列表。验收结束恢复原检查间隔。
